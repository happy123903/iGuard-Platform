# iGuard — iRent 智慧車況檢驗與營運分流系統

iGuard 是一個專為共享租車與車輛營運場景設計的 AI 車況檢驗平台，聚焦在三個核心任務：

- 拍照即時防呆，避免使用者上傳錯誤角度或不完整照片
- 車外與車內 AI 智能判定，識別新損傷、污漬與遺留物
- 自動分流與工單生成，將異常案件轉成清潔或維修派工

本專案的核心價值，不只是「辨識圖片」，而是把車況檢驗變成一個真正能支撐租賃營運決策的系統。

---

## 專案定位

這個專案的目標，是將傳統依賴人工檢查、手動判定與賬本式車況記錄，改造成一套具備視覺 AI、數據化風險分級與營運自動派工能力的智慧車隊系統。

在共享租車場景中，最常見的問題不是單純照片拍得不清楚，而是：

- 使用者拍照角度錯誤，造成判斷錯誤
- 車輛在地下室或夜間暗光環境下照出來模糊且低對比
- 車損細節很小，肉眼不容易判斷是否為新損傷
- 車內垃圾、污漬與私人物品容易被混淆
- 站點人員無法在短時間內快速知道該放行、修理還是清潔

iGuard 的設計，正是要把這些問題從「靠人眼判斷」轉為「AI+流程自動判定」。

---

## 解決的痛點

### 1. 拍照品質不穩定

電動車、租車場景中，使用者拍攝角度、距離、光線、手機穩定度都不一致。這會導致：

- 全車照與車牌不完整
- 車身遮擋過多
- 照片暗、模糊、過曝
- 無法有效比對借還車狀態

本系統設計了拍照防呆層，會在圖片進入大模型前先檢查是否符合規範，避免錯誤資料污染下游判讀。

### 2. 車損判定難、誤判多

傳統車況判定中，最難的部分不是把「有沒有損傷」判斷出來，而是：

- 損傷是否是新產生
- 是刮痕、凹陷還是反光噪音
- 是路面雜訊還是真正車身受損

在現實照片中，反光、陰影、輪圈、車牌邊緣與路面特徵都會被誤判為損傷。iGuard 透過多模型結合方法降低這種誤報，將車損候選區先做幾何與像素層級濾波，再交給更強的視覺模型做最後判斷。

### 3. 車內整潔判定語義模糊

車內場景的複雜度遠高於車外：

- 寶特瓶、紙杯、飲料杯可能被誤認為常規雜物
- 雨傘、背包、外套等私人物品不一定屬於髒污
- 污漬、灰塵、泥沙、遺留物都需要有所區分

這正是多模態大模型的價值所在：它不只是看「有沒有東西」，而是理解這個東西在車內場景中的含義，並輸出可解釋的判定結果。

### 4. 異常沒有快速派工機制

車況判定若只停留在「看圖」層面，實際營運仍然無法落地。真正需要的是：

- 判定為異常時如何派工
- 是清潔、修理、還是人工覆核
- 工單要如何記錄證據、影像、受損位置與狀態變更

本專案把判定結果直接與工單、車輛狀態機、資料庫整合，讓 AI 判斷能轉成真正的營運行動。

## 技術架構

### 1. 前端層

前端採用靜態 HTML/CSS/JavaScript 架構，定位為使用者操作介面與影像上傳入口，重點是：

- 車況拍照與圖片提交
- 拍照防呆提示
- 檢驗結果呈現
- 工單與車輛狀態展示

這一層不承擔模型推理，保持簡潔與快速載入，同時適合部署到 GitHub Pages 等靜態託管平台。

### 2. 雲端資料層

資料層使用 Supabase，提供：

- PostgreSQL 資料庫
- Storage 圖片儲存
- Realtime 即時更新
- 後端 API 讀寫資料的統一入口

這讓系統能將車況紀錄、工單狀態、車輛狀態與影像 URL 儲存在統一資料層中，方便後續營運平台、管理端與數據分析對接。

### 3. AI 推理層

本地 FastAPI 後端在 RTX 5090 上運行，整合了以下核心能力：

- 車輛拍攝品質檢查
- 低光增強
- 構圖與車牌驗證
- 車外損傷檢測
- 車內多模態整潔度判定
- 三層風險分流與工單生成

這是整個系統的核心引擎，負責把原始車輛視覺資料轉成可運營的判定結果。

> **目前模型狀態**：本專案現階段使用的深度學習模型皆為既有的通用預訓練權重，尚未使用本競賽資料集的車損標註資料進行完整的領域微調或重新訓練。因此，模型在真實租車照片、特定車款、拍攝角度、光線與車損型態上的預測結果，可能不如預期，輸出應視為輔助判讀與流程驗證結果，而不是最終的專業估價或事故責任判定。

## 模型現況、限制與演進方向

### 目前採用的預訓練模型與方法

iGuard 的創新重點不在於宣稱已經訓練出一個專屬車損模型，而在於將多個既有能力串成一條完整的車況檢驗與營運流程：

| 模組 | 目前使用的模型／方法 | 在流程中的角色 |
|---|---|---|
| 車輛構圖與視角守門 | YOLOv11x-seg 預訓練權重 | 偵測車輛、取得車身遮罩、檢查主體比例與拍攝構圖 |
| 借還車影像對齊 | SuperPoint + LightGlue 預訓練特徵；必要時退回 SIFT | 對齊不同時間拍攝的借車與還車影像，降低角度差異 |
| 車損候選區與遮罩 | SSIM／高頻差分、幾何與像素篩選，搭配 SAM 2 Large 預訓練權重 | 找出可能新增的差異區域並產生像素級遮罩 |
| 車內整潔與物品語義判讀 | Qwen2.5-VL-3B-Instruct 預訓練多模態模型 | 分辨垃圾、污漬與疑似遺留物，輸出整潔度與處置建議 |
| 暗光影像處理 | Zero-DCE 官方預訓練權重或影像增強備援流程 | 改善地下室、夜間等低光影像的可辨識度 |
| 風險分流與派工 | 規則式三色決策矩陣 | 將辨識結果轉成綠色放行、黃色覆核或紅色派工 |

換言之，目前的車損判定是「借還車影像對齊 → 差異候選區生成 → 遮罩與幾何篩選 → 車損嚴重度閾值分級」的組合式流程；車內判定則是透過結構化提示詞引導通用視覺語言模型輸出 JSON，再交由風險矩陣轉成營運動作。這種設計讓系統即使尚未擁有大量專屬標註資料，也能先完成端到端的產品流程驗證。

### 為什麼目前預測結果可能不如預期

預訓練模型通常是在通用資料或不同任務上學習，未必充分理解共享租車場景中的細節。例如：

- 通用車輛偵測與分割模型不一定熟悉競賽資料中的車款、拍攝距離與車身局部特徵。
- 反光、陰影、光線變化、拍攝位移與壓縮雜訊，都可能被差分流程誤認為新增車損；反過來，細小或低對比刮痕也可能被漏掉。
- SAM 2 擅長依提示分割視覺物件，但它本身不是針對「車損類別」訓練的判定器，無法單獨保證遮罩就是損傷。
- Qwen2.5-VL 能理解一般車內語義，但對「日常使用痕跡與必須派工的髒污」的界線，仍可能受到照片品質、視角與提示詞影響。
- 現有嚴重度與風險分級包含閾值與規則，能讓流程可執行，但不等同於經過人工專家一致驗證的車損量化標準。

因此，現階段的評估重點應放在流程是否完整、輸入品質是否可控、結果是否能提供人工覆核依據，以及是否能成功觸發正確的營運分流；不應只用單次預測結果推論模型已具備生產環境等級的準確率。

### 為何現階段選擇預訓練模型仍是合理方案

若要訓練真正適合 iRent 車況檢驗的專屬模型，必須先建立大量且一致的資料標註，例如車損位置、類型、面積、嚴重度、是否為新增損傷，以及車內垃圾、污漬與遺留物的分類。這項工作有兩個現實門檻：

1. **標註成本高**：車損往往需要放大檢視、描繪區域與比對借還車影像，單張照片的處理時間遠高於一般物件分類。
2. **判定具有主觀性**：刮痕、反光、髒污、舊傷與新傷之間可能沒有明確邊界，不同標註者對位置與嚴重度也可能產生差異，需要制定規範、交叉複核與一致性校準。

此外，本競賽 dataset 並未提供可直接用於車損監督式訓練的完整標註資源。在缺乏可靠 ground truth 的情況下，貿然訓練自己的模型可能只是把不一致的主觀判斷學進權重，未必比通用預訓練模型更可靠。基於上述成本、資料品質與時間限制，現階段先採用預訓練模型，搭配影像品質防呆、跨時間影像比對、幾何／像素篩選與人工覆核，是較務實且能快速驗證產品可行性的選擇。

### 後續自有模型的建議路線

當系統累積足夠的實際案件與人工覆核紀錄後，可建立標註規範與分階段資料閉環：

1. 定義車損類別、車身部件、嚴重度與「是否新增」的標註規則，並以雙人標註與專家仲裁降低主觀差異。
2. 先以目前流程產生候選區與預測結果，讓人工只需修正或確認，降低從零開始標註的成本。
3. 累積高品質標註後，針對競賽資料與實際車隊影像微調車輛／車損偵測、分割或分類模型。
4. 以獨立測試集、不同光線、不同車款與不同拍攝角度驗證 precision、recall、漏判率與誤報率，再逐步替換通用模型。
5. 保留目前的品質守門、對齊、風險分流與人工覆核機制，讓自有模型成為可替換的推理元件，而不是重新建立整套營運流程。

在有足夠且一致的自有標註資料後，專屬模型理論上能更貼近 iRent 的車款、拍攝規格與營運定義，預期會比直接套用通用預訓練模型有更好的辨識效能與穩定性；但這項改善必須透過嚴謹資料治理與獨立評估驗證，不能僅以模型改名或單次案例推論。

## 系統流程

本系統的運作可以概括為三個階段：

### 第一階段：拍照防呆

在照片進入辨識模型之前，先判斷：

- 是否模糊
- 是否過曝或低光
- 是否偏離車輛建議拍攝角度
- 車牌是否完整入鏡
- 車輛主體是否被正確包含在畫面中

如果不合格，系統會立即提示重拍，而不是繼續把錯誤資料送進後續模型。

### 第二階段：車況判定

- 車外照：對比借還車影像，檢測是否有新增車損
- 車內照：識別髒污、垃圾與私人物品
- 車牌與構圖：驗證資料與訂單是否一致
- 風險評分：分成綠色、黃色、紅色三種判定層級

### 第三階段：營運分流

- 綠色：自動放行
- 黃色：人工複核
- 紅色：立即觸發工單與整備處理

這個階段讓模型不只是做評估，而是直接接入營運，而不是停留在研究原型。

## 為什麼這個系統值得做

### 1. 顛覆傳統人工車況檢查

傳統上，車況檢查依賴現場人員肉眼觀察，耗時長、主觀強、易有漏判與誤判。這種流程在租賃場景中尤其不穩定，因為車輛狀況是高頻、重複、需要標準化的。

### 2. 讓車況檢查可量化

這個系統把車況判定轉化成可量化的：

- 亮度、模糊度、構圖指標
- 車牌核對結果
- 損傷區域與嚴重度
- 車內清潔等級
- 風險分級

這些結果可直接支撐後續流程與數據分析。

### 3. 將 AI 從展示型轉成營運型

很多 AI 專案最後停在「可以識別圖片」的層面，難以落地。iGuard 的重點不是展示模型效果，而是：

- 判定後如何寫入資料庫
- 如何產生工單
- 如何更新車輛狀態
- 如何讓人員快速處理異常

這使它更接近實際營運系統，而不是單一 Demo。

### 4. 在資料不足時先驗證完整閉環

即使目前尚未有足夠的專屬標註資料，iGuard 仍先完成「拍攝防呆、影像處理、模型判讀、風險分流、資料留存與工單派送」的完整閉環。這使團隊可以先驗證實際營運流程與人工覆核介面，並在日後取得高品質標註後，逐步將通用預訓練模型替換成更符合車隊需求的自有模型。

## 專案亮點

- 本地 AI 架構，避免過度依賴雲端計算資源
- 以多個預訓練模型與影像處理方法組合出可落地的車況檢驗流程
- 以現實租車場景影像為核心設計，非純學術 Demo
- 零光源與暗光場景都納入考量
- 損傷與車內整潔分開處理，降低誤判風險

- 明確保留模型限制與人工覆核位置，方便後續建立標註資料閉環
- 讓車輛狀態、工單、影像與評估結果成為一套完整系統

## 未來展望

iGuard 目前先以預訓練模型與完整的營運流程驗證為主，未來將從「能夠執行檢驗」逐步發展為「更精準、更可量化、能持續學習的智慧車隊平台」：

### 1. 建立高品質車況標註資料集

透過實際案件與人工覆核紀錄，逐步累積車損位置、損傷類型、嚴重度、是否為新增損傷，以及車內垃圾、污漬和遺留物等標註資料。未來會建立明確的標註規範、雙人交叉標註與專家仲裁流程，降低車損判定的主觀差異，讓資料能真正用於模型訓練與客觀評估。

### 2. 訓練符合車隊場景的專屬模型

當標註資料量與一致性達到要求後，可針對 iRent 的車款、拍攝角度、光線條件與常見損傷型態，微調或訓練專屬的車輛偵測、車損分割與車內物品分類模型。相較於直接使用通用預訓練模型，自有模型預期能更貼近實際營運定義，但仍須透過獨立測試集驗證 precision、recall、誤報率與漏判率。

### 3. 建立 AI 與人工協作的資料閉環

將黃色待審案件的人工覆核結果回寫為後續訓練資料，並記錄模型預測、人工修正、最終處置與工單結果。透過這個流程，可以優先挑選模型最不確定或最容易誤判的案例進行標註，逐步形成主動學習與持續改善機制，而不是只在專案初期一次性建立資料集。

### 4. 提升多視角與跨時間比對能力

未來可進一步整合同一台車的多個外觀角度、借車與還車時間序列、歷史損傷紀錄與車輛部件位置，建立更完整的車況基準。這能協助系統區分既有傷痕與新增損傷，降低單張照片、光線變化或拍攝位置不同所造成的誤判。

### 5. 強化部署、監控與營運整合

在模型效能穩定後，可持續完善模型版本管理、推理延遲監控、資料品質監控與異常告警，並將結果更深入整合至租車預約、站點整備、維修排程與客服失物流程。未來也可依站點、車款與環境條件分析模型表現，讓營運人員能掌握系統的適用範圍與改善優先順序。

最終目標不是完全取代人工，而是讓 AI 負責高頻、可標準化的初步檢驗與案件分流，讓人員把時間集中在高風險、低信心或需要專業判斷的案件上。透過資料、模型與營運流程的持續迭代，iGuard 才能從目前的創新概念與流程原型，逐步成長為可靠的智慧車況管理平台。

---

## 結語

iGuard 的核心不是單一模型，而是一個完整的車況檢驗與營運決策系統。它把影像辨識、資料管理、異常分流、工單生成串在一起，目標是讓共享租車業務中的車況判定變成一個穩定、可操作、可量化的自動流程。

如果把這個專案視為一個產品，而不是一個單純 AI 演示，這份系統的價值就在於：

- 它能降低人工檢查成本
- 它能提升車況判定一致性
- 它能把車損誤判與漏判集中到可追蹤、可覆核、可持續改善的流程中
- 它能讓營運部門用更快的速度處理異常案件

目前模型仍以通用預訓練權重為主，預測結果不一定符合所有實際車況，這是現階段必須正視的限制；但 iGuard 已經提供一套可運作的創新流程。未來若能透過實際案件建立一致且高品質的自有標註資料，再以這些資料訓練或微調專屬模型，將有機會進一步提升車損辨識、車內整潔判定與營運分流的效能。這也是本專案從流程驗證走向生產級智慧車隊系統的主要演進方向。
